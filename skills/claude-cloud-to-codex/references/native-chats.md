# 将可核对的云端对话导入原生聊天

适用于 Claude 的项目主对话、讨论串或分支已经可以完整读取，并且目标是本机已有的 Codex 项目。每个有独立来源 ID 的对话对应一个原生聊天。用项目和讨论的稳定 ID 识别改名、同名、跨项目重名。只收回项目列表或摘要时，先完成正文取证。

## 准备输入

在本机临时目录写一份 UTF-8 JSON。下面只含虚构数据。把 `root` 替换为能在 Codex 桌面项目列表里核对、且已经存在的本机绝对目录。Windows 的 JSON 路径可用正斜杠。

```json
{
  "version": 1,
  "projects": [{
    "sourceId": "example-project-A",
    "root": "D:/Projects/Example",
    "chats": [{
      "sourceId": "example-discussion-1",
      "sourceUrl": "https://example.invalid/conversations/1",
      "title": "海岸场景讨论",
      "messages": [
        {"role":"user","text":"保留这两段。\n\n第二段。","timestamp":"2026-03-01T09:40:00+08:00","meta":{"precision":"minute"}},
        {"role":"assistant","text":"【Claude 历史界面记录】\n任务已暂停","meta":{"kind":"interface","sourceIndex":2}}
      ]
    }]
  }]
}
```

- 逐串按来源顺序排列。保留两个相邻的用户消息或助手消息、换行、尾部空白、代码块和转发关系。界面事件可单列成带清楚来源标签的显示记录。示例中的 `role: "assistant"` 是让状态卡在目标端显示所用的映射；在 `meta` 中保留原类别、原作者（未知可省略）和原始序号，验收时单独统计。转发保留来源关系。不得把源站的工具调用转成 Codex 会执行的动作。
- `timestamp` 可选，要求日期、时间和明确时区。只有日期或未知时区时，省略它，把原显示值和精度存入 `meta`。未知时间的行留在原来的序号。Codex 侧栏或原生消息有时显示导入时刻；来源时刻另存在原生来源元数据。
- 附件已有文件时，先校验字节数和 SHA-256，再在相应消息的 `meta` 记录文件名、哈希、已验证的最终本机路径及可见来源引用。只有引用时记下引用和不可下载的结果。本工具保存这些元数据，获取二进制和验证文件内容由文件恢复步骤负责。
- 运行前盘点已有 Codex 项目聊天。标题相同或相近时比较稳定来源标记、项目根目录、逐条角色和全文。一条确证重复的历史可在这个 chat 对象提供 `existingThreadId`，脚本会严格校验目标项目和完整历史后补上来源绑定。遇到同一来源已有内容发生变化、目标已绑定另一个来源、有两个候选或来源不能确定时，保留现状，先核对差异。已导入的聊天若由用户继续聊过，也不要以旧快照覆盖。
- 输入、临时 JSONL 和本机附件路径可能含私人内容。使用仅本人可访问的临时目录，把它们排除在公开仓库和同步盘之外。

## 隔离演练

需要 Node.js（实测使用 Node 24）及能够启动 `codex app-server --stdio` 的本机 Codex 可执行文件；不依赖 npm 包。若 PATH 只有不可直接启动的包装脚本，可把 `CODEX_BIN` 设成同安装版本受信任可执行文件的绝对路径。

从 skill 文件夹先运行自测，再验证本次清单。

```text
node scripts/self-test.mjs
node scripts/native-chats.mjs verify <私有清单.json>
```

首次在新环境执行时可先跑自测。它自建两个虚构项目和四个对话，检验助手开场、纯助手对话、跨项目同名同 ID、重复执行和已变化来源的拒绝处理。自测还将父环境的 SQLite、Claude 和 XDG 等目录指向另一份临时数据，验证隔离演练不会读写其中的状态，两份源项目意外指向同一目标根目录也会被拒绝。

`verify` 使用你准备的清单。它在本机临时目录建立独立的 Codex 状态和发现用 profile，给临时状态建测试项目，将同一批选择导入两次并核对线程 ID。它逐条验证角色与原文、项目路径、标题、来源标记和元数据。程序正常退出时清理本次启动新建的隔离目录。演练成功代表当前这套二进制和输入通过，正式账户和桌面侧栏需要在后续步骤检验。

本例在带实验性接口的 Windows 桌面/CLI 上验证。其它版本可先用本机 `codex app-server generate-ts --experimental --out <临时目录>` 核对协议。需要 `externalAgentConfig/import`、异步 `externalAgentConfig/import/completed`、`thread/read`、`thread/name/set`、`thread/metadata/update`、项目查询和 thread attachment 增查及来源反查。助手开场还需 `thread/fork` 支持按本机临时源文件创建原生聊天。方法、回执或读取结构不兼容时停止正式写入，保留已经确认的源数据并向用户说明具体能力缺口。若用户希望改成可查阅的离线归档，再单独交付。

## 正式导入并把聊天归入侧栏

1. 确认用户授权导入这些具体源项目及聊天，并核对正式目标目录、桌面项目、版本、主机。清单内每个 `root` 在正式 app-server 的 `project/list` 中必须唯一；随后按它返回的 ID 通过 `project/read` 复查根目录。重名项目用根目录区分。若用户还没有建立目标项目，先依其要求创建或选定，脚本不在正式账户推测或创建项目。
2. 正式操作需要目标 Codex 状态目录写入权限，以及一个项目目录外、Codex 状态目录外的私有暂存目录。首次使用的暂存目录应为空，重试沿用同一目录。受沙箱约束时仅申请该次导入所需的路径或命令权限。目标 Codex 状态目录是启动本机 Codex 使用的 `CODEX_HOME`，未自定义时是用户目录下的 `.codex`。从 skill 文件夹执行本次导入。

   ```text
   node scripts/native-chats.mjs apply <私有清单.json> <私有暂存目录绝对路径> <正式Codex状态目录绝对路径>
   ```
3. 程序先对本次输入重做隔离演练，在正式库只读核对所有已有绑定，再逐串导入。子进程只转发基本系统环境变量；其 Claude、XDG、临时目录和日志使用私有 profile，SQLite 明确指向选定状态，并核对 app-server 的有效配置与管理要求。若本机实际使用单独的 SQLite 目录、存在无法鉴别的存储重定向或受管位置冲突，先停止并核实当前桌面的真实存储，不要删除用户环境变量强行通过。对用户开场的聊天，只向迁移接口提交本次选定的一条 `SESSIONS` 记录。其它导入项数组为空。若自行使用 `externalAgentConfig/detect`，按本次的源 JSONL 绝对路径和目标项目路径做交集，不能直接提交探测到的所有项目和设置。
4. 等到同一 `importId` 的完成通知，核对源文件和原生聊天 ID。逐串用 `thread/read(includeTurns=true)` 回读所有消息，与输入的角色、正文、顺序逐项比较。这个版本会额外显示一条系统导入尾标；仅在原消息数已吻合、末尾确实多一条导入标记时忽略它。程序用项目来源 ID 与聊天来源 ID 合成唯一键，写入外部来源附件，并用 `thread/attachmentOwner/list` 验证恰好对应一条聊天。成功输出包含项目来源 ID、聊天来源 ID、原生聊天 ID 和源消息数。
5. **桌面项目需另验。** 用桌面连接器 `list_projects` 按同一本地路径查到桌面项目 ID。在实测版本里，它与 app-server 的项目 ID 属于不同命名空间。对上一步的原生聊天执行桌面 `read_thread`，核对原题、工作目录；需要时用 `move_thread_to_project` 绑定桌面项目。最后分页读 `list_threads`，确认每个新聊天都出现在预期桌面项目 ID 下。脚本执行到原生存储读回为止，桌面绑定和验证由运行 skill 的 Codex 完成。
6. 报告各项目的源聊天数、消息数、核对情况和未取回的具体附件。清理本次私有暂存和清单前，确认正式聊天和实际附件均可读；只删除本次明确创建的目录。来源链接和时间保存在聊天的原生元数据，用户无需另行维护一份迁移文档。

## 两个容易错报成功的情况

**对话第一条是助手发言，或整串只有助手发言。** 部分外部导入器从第一条用户消息才开始显示。脚本在隔离状态中临时加一个唯一的起始标记，转换后先核对包含该标记的整串。然后只在临时副本中移除经核实属于标记的两种事件，并验证数量和会话元数据，用 `thread/fork` 从净化过的临时副本生成正式聊天。输出角色、原始行数和全文必须逐项相同。脚本不会把临时用户发言写入正式聊天，也不直接编辑正式 rollout。遇到未知事件结构会中止。

**按 ID 可读，桌面侧栏却找不到。** 先对已存在的 ID 用桌面 `set_thread_title` 重新设置原题以刷新缓存，再尝试移动和列表读回。一次实测中，两条纯助手对话的原生内容和项目正确，原生列表缺少非空 `preview`。可以依次检查这三个位置。

1. 在隔离库用一条纯助手样本复现，比较 `thread/read`、普通 `thread/list`、项目过滤列表及桌面结果。检查当前构建是否已有支持的预览修正接口，优先使用。
2. 该特定构建可将真实助手首句写作侧栏预览，同时保留空 `first_user_message` 与原用户事件标志。在正式数据上修复属于单独的本地索引写操作。只有经用户授权、隔离样本证明当前版本确实有相同字段和效果、而且能回滚时再做。记录精确的线程 ID、项目 ID、当前预览、来源绑定、rollout 散列，并在短事务中只更新这些聊天的空预览；核对并发前值，遇到既有非空预览即停。不要改聊天正文、时间、真实角色或用户事件标记。读回失败，按比对过的值回滚。随 skill 提供的导入器不带通用数据库补丁。
3. 用普通和按项目过滤的列表查询，重新核对原生正文和 rollout 散列。随后用桌面 `set_thread_title` 重设原题，`move_thread_to_project`，再读 `list_threads` 逐条确认。只有底层可读而侧栏仍缺少时，交付已有的原生聊天入口并明确侧栏归属尚未验证。

## 中断、重复导入与来源冲突

成功的重复执行先按稳定来源键反查，再核对正文、元数据及项目归属，已有聊天不会新建。对于尚无来源绑定的早期导入，先完成上面的桌面盘点和 `existingThreadId` 映射。工具不会靠相同标题猜测两个聊天是同一个。

脚本每次只操作一串。发出有副作用的请求后若出现超时、崩溃或回读不一致，将在目标状态目录留下与该来源唯一对应的 `.claude-cloud-import-*.lock`，用于阻止盲目再建。保留暂存区，确认前一次进程已经退出，读取该标记里的来源和原生 ID（若已收到）。检查该来源的反向绑定、导入完成回执，或对应版本的只读导入账本；助手开场的分支还可按原生 `forkedFromId` 与工作目录核对。只有确认一个或零个匹配、角色全文一致、来源绑定和标题/项目状态已补齐或已明确待补齐后，才移除**该来源**的中断标记。可将已确认且尚无来源绑定的目标填为 `existingThreadId` 再继续。已产生目标却无法确认归属时，告知用户具体冲突，保留现有聊天。
