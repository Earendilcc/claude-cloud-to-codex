# 恢复项目后，如何继续开发

当用户问“云端看起来更新，要覆盖本机吗”“开发目录里还有哪些东西没进正式版”时，先做只读对照。若用户只要求迁移或答疑，做到能回答就够了。把旧工具接入工程、改排期、合并分支或清理历史包，都属于后续开发操作，要按用户实际要求进行。

## 1. 为每种“版本”找到证据

| 找到的内容 | 先查什么 | 能据此确定什么 |
| --- | --- | --- |
| 本机工作树 | 实际工程根、当前分支、未提交和未跟踪的文件 | 用户此刻真正使用和修改的内容 |
| Git 仓库 | 默认分支、实际交付或开发分支、两者的共同祖先、未合并的 PR | 某提交包含哪些改动，以及它是否已经合入默认分支 |
| 云端正式源码、构建物和说明 | 原目录、来源消息、同版源码和成品是否成套 | 哪些是当时交给用户使用的版本 |
| 开发进度包、生成器、测试和旧交接包 | 逐包列出成员，查入口、依赖、内部目录、生成目标和基线版本 | 哪些是独立工作、可恢复工具、旧版产物或重复内容 |

先清点用户选定的目录及压缩包，保留完整相对路径和同名文件。统计时分清“几个压缩包”和“包内几个文件”。一个列了许多路径和校验值的清单，可能只随包交付了一份成品；逐个检查包成员，清单里的摘要无法反推出缺失的文件。按源文件识别项目归属后再做对照。

以下命令以虚构目录为例。替换路径、远端和分支名后，在 PowerShell 中运行。前几条只检查本机已有的 Git 引用。

```powershell
$repo = 'D:\Demo\Island'
git -C "$repo" status --short --branch
git -C "$repo" branch --all --verbose --no-abbrev
git -C "$repo" log --oneline --left-right origin/main...origin/feature-coast
git -C "$repo" merge-base origin/main origin/feature-coast
git -C "$repo" ls-tree -r --name-only origin/feature-coast
```

远端跟踪引用可能已经过期。需要判断“远端**现在**的版本”时，用现有只读仓库接口查询候选分支的当前提交，或在已获网络权限时运行 `git -C "$repo" fetch origin` 更新跟踪引用，再比较。缺少这项证据时写明只核实了本机上次获取的提交。本机源码有时与开发分支一致，默认分支仍落后一次提交，三者应分别给出结论。

## 2. 按相对路径和内容确定差异

1. 用云端相对路径找到本机候选。区分缺失路径、仅大小写不同、同名异目录和同路径异内容。比较多个云端进度包时保留各自的来源，以免后解开的同名文件掩盖差异。
2. 对同路径的原始字节计算 SHA-256。二进制、压缩包、构建物用原始哈希。对明确的文本文件，若字节不同，再用已知编码解码，**只统一 CRLF 和 LF** 对照。报告“仅换行不同”并保留原始哈希。时间、大小和规范化后的文本均不能证明两个原件字节相同。
3. 对有实质差异的同一文件，找可信共同基线。来源可以是包标注且核实过的 Git 提交、上一版完整交付或原始快照。分别检查“基线 → 本机”和“基线 → 云端”，识别本机独有改动、云端独有改动和冲突。找不到共同基线时，列出差异及依据，留下两份原件，暂缓有冲突的替换。

```powershell
$local = 'D:\Demo\Island\src\scene.js'
$cloud = 'D:\ImportStaging\release\src\scene.js'
$baseFile = 'D:\ImportStaging\baseline\src\scene.js'
foreach ($file in @($local, $cloud)) {
    Get-FileHash -LiteralPath $file -Algorithm SHA256
}
git diff --no-index -- "$baseFile" "$local"
git diff --no-index -- "$baseFile" "$cloud"
git merge-file --diff3 -p -- "$local" "$baseFile" "$cloud"
```

`git diff --no-index` 在有差异时返回 1。`git merge-file -p` 将合并建议输出到终端，适用于文本；正常合并返回 0，有冲突时输出冲突标记并返回非零。检查结果后再决定是否把已确认的变动写进目标。多个任务共用工作树时，在写入前复核所涉及文件仍与读入时相同。

## 3. 独立处理源码、开发包和成品

- **正式源码相符，云端显示更新日期较晚。** 保留正在使用的本机文件，报告原始哈希或换行比较的结果。若用户还问实际版本，进一步核验仓库提交和构建物。
- **进度包同时带来新资产和旧代码。** 例如云端包有新角色模型，随附的角色控制器却基于上周源码。保留可续作的包和原内部结构，查清新资产、依赖、接入条件、待确认事项。用户要求整合时，从当前工作树挑入已确认部分，再处理与现有控制器的冲突。角色预览、自查和接入可运行版本分别记录状态。
- **开发目录有生成器或测试。** 先查脚本读写哪些文件、旧绝对路径、平台依赖、需不需要浏览器。生成器先对临时副本运行，按关卡、配置项或记录键比较生成结果和正式配置；生成数据已经交付，就无需再向正式配置重复添加。旧测试须指向当前应用并通过常用入口执行。例如让原先只在云端运行的浏览器回归读取本机配置，运行真实场景，检查断言结果。能在目录里找到脚本只证明文件已经恢复。
- **交接目录只有旧成品、路径清单和历史校验值。** 留作版本比较时保留版本关系。用项目已有的构建命令从确切的源码版本重新构建，分别核对成品、说明和交付清单。可复现构建比原始字节；若构建嵌入时间戳等变动字段，指出具体差异，补跑功能测试，同时保留原件。无需用旧可执行文件覆盖新版。

若用户要求恢复整套开发流程，先阅读已恢复脚本的命令、依赖和写入位置。分别在独立工作副本验证项目原有逻辑测试、真实界面回归及交付命令；对比交付目录与预期相对路径、字节数和哈希。脚本通过后再接到正式项目入口。安装依赖、启动浏览器、写正式工程或访问私有远端，各用相应范围的权限。

## 4. 按已有分工接续，按验收结果清理

查看现有设计文档、原生项目记忆及有时间的分工消息。对每项工作单独找最近的交付、测试、评审或阻塞证据。早期线性计划可能被后来的并行分工更新；例如场景可以独立施工，角色替换须待预览确认，两个任务可以处于不同阶段。已有文档足以表达这些状态时直接沿用。用户授权更新且确有缺项时，只补现有文档的对应位置，保留旧决定的时间和后续变更，不把所有“待开发”改写成一批同时执行。

最后分别说明哪些已交付、哪些只存在于开发包、哪些已在当前工程重新验证、哪些还缺证据。校验过目标路径、内容和常用入口之后，清理本次创建的临时比较目录。历史交付、用户已有文件、唯一可恢复的开发快照按约定留存；用户明确要求移除时，先确认没有仍待恢复的唯一内容，再仅处理约定对象。发布游戏、合并 PR、推送业务仓库等外部动作须单独在当前任务范围内。
